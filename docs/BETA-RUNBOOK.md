# 14명 베타 운영

## 개시

- 배포/자동 테스트/스테이징 권한 테스트 통과 기록을 확보합니다.
- 운영자 1명, 장애 대응자 1명, 삭제·내보내기 문의 담당자를 지정합니다.
- 14명 각각 계정 생성 및 이메일 확인. 운영자가 크루 생성, 초대 코드를 개별 전달하고 승인합니다. 자동 공유 동의는 하지 않습니다.
- 데이터 처리 목적, 비공개 GPS, 크루 집계에 포함되는 항목(거리·횟수), 동의 철회/계정 삭제 경로를 안내합니다.
- 참가자별 첫 GPX의 수치가 원래 러닝 앱과 크게 다른지 확인하며 장치별 오차를 기록합니다. sample을 실제 운동으로 집계하지 않습니다.

## 매일/매주

매일 API health, queued/processing 최대 대기시간, failed 비율, Storage/DB 용량, 인증 email 실패, 요청 오류를 확인합니다. 원본 GPS나 심박을 로깅하지 않습니다. 큐 지연이 5분을 넘으면 worker/DB 연결부터 확인하고 파일 읽기 오류는 최대 3회 재시도 후 사용자에게 삭제·재업로드를 안내합니다.

매주 가입/승인·업로드 성공·계획 생성/완료 비율, 사용자가 보고한 계산 차이와 UI 오류를 검토합니다. 초대 코드는 7일 만료하며 외부 채널에 공개하지 않습니다. 크루 관리자 지정은 owner만 수행합니다.

## 삭제/보존/복구

소유자는 크루 소유권을 양도한 뒤 계정을 삭제합니다. 파일 삭제는 원본과 분석을 함께 지웁니다. 삭제 API가 외부 Storage/Auth 오류로 실패하면 완료를 표시하지 말고 재시도합니다. 분산 transaction이 아니므로 부분 삭제 후 원본 링크가 잠시 실패할 수 있습니다. 운영자는 DB run 파일 목록과 Storage 경로를 정기적으로 비교하고, DB가 없는 orphan 파일은 생성 시각 유예 24시간 및 worker 작업 유무를 확인한 후 삭제합니다. 삭제 요청을 백업 복구로 부활시키지 않도록 별도 삭제 요청 처리 기록을 최소 정보로 유지하세요.

Supabase의 DB backup/PITR 플랜과 private Storage 백업은 별개입니다. 운영 정책에서 보존 기간과 삭제 후 백업 잔존 기간을 명시하세요. DB+Storage 복구를 스테이징에서 시험하고 Auth/프로필/원본 참조 무결성을 점검합니다. 이 저장소가 백업 서비스를 자동 생성하지는 않습니다.

## 장애와 확장

worker 중단: 기존 처리 lease가 120초 후 복구되어 재선점됩니다. HTTP 요청 process의 BackgroundTasks에 의존하지 않습니다. 반복 실패 fixture는 익명화된 좌표·시각을 별도 동의로 재현한 뒤 알고리즘 회귀 테스트에 추가합니다.

일반 러너/다수 크루로 확장할 때 profile PK/crew membership 복합 PK를 유지합니다. 원본 RLS를 운영자 권한으로 넓히지 않습니다. 큐 backlog 기반 worker 증설, 분석 비용 관측, 날짜별 analysis 요약 index, 장시간 ZIP export를 백그라운드 작업화, 분산 rate limiting을 적용합니다. 훈련량 변화는 일반 안내이며 의료/재활 처방으로 확대하지 않습니다.
